# 권한 규칙 문서

## 1. 목적

이 문서는 화면/기능별 권한 제어를 DB 기반으로 운영하기 위한 규칙을 정리한다.

## 2. 기본 원칙

- 로그인하지 않은 사용자는 기본적으로 접근 권한이 없다.
- 권한은 화면 이름이나 역할 이름이 아니라 프로그램 단위와 기능 액션 기준으로 판단한다.
- 하나의 계정에 여러 역할이 있더라도 권한은 OR 방식으로 집계한다.
- 권한 정책은 UI에 하드코딩하지 않고 DB 값으로 관리한다.

## 3. 권한 소스

권한은 다음 DB 구조를 기준으로 관리한다.

- sys_role_program_permission: 프로그램별 권한값 저장
- sys_user_role: 사용자-역할 매핑
- sys_role: 역할 정의

권한 필드는 다음과 같다.

- canRead: 조회 권한
- canWrite: 작성 권한
- canUpdate: 수정 권한
- canDelete: 삭제 권한
- isOpen: 노출 권한

## 4. 인증/전달 방식

로그인 시 백엔드에서 사용자의 역할과 권한을 응답에 포함한다.

- roles: 사용자에게 부여된 역할 목록
- permissions: 프로그램별 권한 맵

프론트는 로그인 이후 공통 권한 훅을 통해 권한을 읽어 화면에 반영한다.

## 5. UI 처리 규칙

- 권한이 없으면 버튼은 숨기거나 비활성 처리한다.
- 수정 권한이 없으면 편집/저장 관련 액션을 노출하지 않는다.
- 삭제 권한이 없으면 삭제 액션을 노출하지 않는다.
- 권한은 role 이름이 아니라 DB 값 기준으로 판단한다.

## 6. 액션 코드 기준

화면은 역할 이름 대신 액션 코드로 권한을 요청한다.

- edit / save: canUpdate 또는 canWrite
- delete: canDelete
- cancel: 기본적으로 허용

즉, 화면은 “이 버튼이 어떤 액션을 하는가”를 기준으로 권한을 물어보고, 백엔드/DB 권한값과 매핑한다.

## 7. 적용 예시

예를 들어 목회자 소개 화면에서:

- canUpdate 또는 canWrite가 true이면 편집/저장 버튼이 노출된다.
- canDelete가 true이면 삭제 버튼이 노출된다.
- 권한 정보가 없으면 버튼은 노출되지 않는다.

## 8. 운영 기준

- 권한 변경은 DB 값만 바꾸면 반영 가능하다.
- 역할명 변경이 있어도 권한 로직은 유지된다.
- 새 화면이 추가되면 프로그램 ID와 액션 코드 매핑을 정의한 뒤 공통 규칙으로 적용한다.
