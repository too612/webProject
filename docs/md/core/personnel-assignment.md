# 인사발령과 DB 스케줄러

## 업무 범위

- 기존 `/erp/humen/personnelmove` 화면에 **인사발령**, **겸임발령** 탭을 제공한다.
- 겸임은 본 인사와 연결된 독립 원장·사번으로 관리한다. 로그인 후 사번 선택과 ERP 권한 전환은 이번 범위에 포함하지 않는다.
- 부서는 필수 코드 직접 입력, 직급은 필수 공통코드 `102` 선택이다. 부서 코드는 서버에서 유효성을 검증한다.
- 직위·고용형태·직책은 공통코드 선택이며 기본값은 `선택`이다. 미선택은 NULL이고 적용 대상 원장의 기존 값을 해제한다.
- 발령종류 `105-060`은 퇴직으로 반영하며 나머지는 재직이다. 기존 면직 코드의 의미를 퇴직으로 변경하지 않는다.

## 현재 인사정보의 근거

업무 시간대의 오늘까지 도래한 삭제되지 않은 발령을 발령일 내림차순, 발령순서 내림차순으로 정렬한 첫 행이 현재 인사정보의 근거다. 같은 대상·같은 날짜에는 여러 발령을 허용하지만 같은 순서는 중복할 수 없다.

- 오늘 발령 신규 등록 및 현재 유효 발령 수정은 즉시 반영한다.
- 미래 발령은 저장만 하고 발령일이 도래하면 자동 반영한다.
- 현재 유효 발령보다 오래된 과거 이력은 별도 편집 확인과 사유로 정정하며 원장에 반영하지 않는다. 후속 스케줄러도 과거 수정일을 근거로 재반영하지 않는다.
- 종료일은 기록과 날짜 범위 검증에만 사용한다. 자동 복귀·원복·퇴직이나 이전 발령 전환의 근거로 사용하지 않는다.
- 삭제는 `del_yn = 'Y'`로 처리한다. 마지막 이력 1건 또는 유일한 도래 발령을 삭제하여 미래 이력만 남기는 동작은 차단한다.
- 현재 유효 발령 삭제 후에는 직전 도래 발령으로 즉시 재판정한다. 미래·과거 발령 삭제로 현재 기준이 바뀌지 않으면 원장을 변경하지 않는다.
- 등록·수정·삭제와 원장 적용은 대상별 잠금과 트랜잭션으로 보호한다. 수정 버전 충돌은 오류이며 입력을 최신 조회 후 다시 확인해야 한다.

겸임 발령은 본 인사 원장에 반영하지 않고 해당 겸임 원장에만 반영한다. 겸임사번은 본사번의 `_1`, `_2` 순으로 부여하며 삭제된 번호를 재사용하지 않는다.

## 스케줄 운영

업무 구현은 인사 업무 단위 실행 진입점에서 관리하고, 공통 등록기는 DB에 등록된 작업 코드와 허용된 Java 구현체만 연결한다. 클래스명·임의 SQL을 DB에서 받아 실행하지 않는다. 관리 화면은 추후 구현한다.

- 발령 동기화 기본 일정은 매시 00분·30분이며 자정 실행을 포함한다.
- 업무 시간대는 `Asia/Seoul`이다.
- 기동 후와 주기적 실행에서 도래한 최신 발령과 적용 근거를 비교하여 누락을 보정한다.
- DB 일정 변경은 등록기의 다음 갱신 시 예약에 반영된다.
- 중지는 새 실행을 막고 이미 실행 중인 트랜잭션을 강제 종료하지 않는다.
- 스케줄 작업 중지와 **발령 반영 전체의 한시 보류**는 구분한다. 후자는 담당자 저장 시 즉시 반영도 보류한다.
- 보류 기간은 시작 시각 이상, 종료 시각 미만이다. 보류가 끝나면 다음 자동 동기화에서 최신 유효 발령을 반영한다.
- 저장 성공과 원장 반영 성공은 구분하여 안내한다.
- 실행 실패는 기록·로그로 남기고 성공 또는 빈 조회로 숨기지 않는다. DB 정책을 확인할 수 없을 때 반영을 임의로 허용하지 않는다.

예를 들어 오늘 09:00~18:00 반영 보류를 설정하면 오늘 발령도 저장만 된다. 18:00부터 허용되며 다음 동기화에서 반영한다. 보류 만료가 특정 시각의 실행 완료를 보장하지는 않는다.

### 공통 스케줄러 코드 책임

- `SchedulerManager`는 예약 등록·갱신·취소, `SchedulerJobExecutor`는 정책 확인·잠금·실행·이력 기록을 담당한다. 업무 구현은 `SchedulerJob` 계약으로 연결하며 이 책임은 병합하지 않는다.
- 자동 실행의 정책 사유는 `evaluate`, 업무 보류 사유는 `evaluateBusinessHold`의 `SchedulerPolicyDecision`으로 확인한다. 업무에서는 `isEnabled`와 `isBusinessPaused`를 사용한다. `isApplyAllowed`는 업무 보류 여부의 반대값이며 같은 판정 경로를 사용한다.
- 운영 호출이 없던 `requireAllowed`, `requireApplyAllowed`, `requireNotPaused` 편의 메서드와 실행기의 공개 `getInstanceId`는 제공하지 않는다. 인스턴스 ID는 내부 잠금·이력 기록에는 계속 사용한다.
- 기존 `SchedulerJobBlockedException` 소스는 삭제하지 않고 deprecated 타입으로 보존한다. 정책 DB 확인 실패와 실행 잠금 상실 예외는 별개이며 그대로 유지한다. 수동 `runNow` 및 lease 확인 계약도 유지한다.

## 호환성과 검증

- 인사관리·내 인사정보의 본무 발령 이력은 겸임 이력을 제외하고 발령순서까지 정렬한다.
- 공식 선교 조회의 기존 종료일 조회 정책은 유지하며 같은 날의 발령순서와 본무 범위를 명시한다. 원장 자동 복귀 정책과는 별개다.
- 엑셀은 [공통 엑셀 계약](grid-excel.md)의 현재 캐시 행·표시 열 범위로 제공한다. 전체 이력 다운로드·엑셀 일괄 등록·결재·임시저장은 별도 범위다.
- 기존 데이터는 테스트 데이터로 취급하며 최초 동기화에서 최신 도래 발령 적용을 허용한다. 테스트 seed의 미지정 직급은 필수 직급 정책에 맞게 보정한다.
- DB 변경은 제공된 SQL을 순서대로 적용해야 한다. 기존 테이블을 DROP하거나 로그인 계정의 사번 연결을 재작성하지 않는다.

## DB 적용 및 활성화

기존 인사·조직·공통코드·국가·발령 테이블이 있는 환경에서는 다음 순서로 적용한다.

1. [퇴직 코드 추가](../../table/com_code_retirement.sql)
2. [스케줄러 테이블](../../table/sys_scheduler.sql)
3. [발령·겸임 마이그레이션](../../table/hrm_assignment_migration.sql)
4. [스케줄 작업 등록](../../table/sys_scheduler_seed.sql)

신규 환경은 기존 테이블 DDL/seed를 먼저 적용한 후 위 순서를 따른다. 겸임 원장은 마이그레이션에 포함되어 있으며 [독립 DDL](../../table/hrm_concurrent_person.sql)은 정의 참조용으로도 제공한다. 마이그레이션 재실행 시 기존 발령순서와 겸임사번을 재발급하지 않는다.

애플리케이션의 `APP_SCHEDULER_ENABLED=true`로 공통 등록기를 활성화한다. DB 작업의 `is_enabled`는 개별 자동 작업의 활성 상태이며, 전역 등록기 설정과 별개다. 설정 갱신 간격은 `APP_SCHEDULER_RELOAD_DELAY_MS`(기본 300000ms), 첫 조회 지연은 `APP_SCHEDULER_INITIAL_DELAY_MS`(기본 30000ms)다.

### 자동 작업만 중지

`sys_scheduler_job.is_enabled = FALSE` 또는 `sys_scheduler_pause`의 기간을 사용한다. 담당자 저장 시 즉시 반영은 계속 허용된다. 기간은 TIMESTAMPTZ로 저장하고 시간대 오프셋을 명시한다.

### 발령 반영 전체 보류

`sys_scheduler_business_hold`에 `business_code = 'HRM_ASSIGNMENT'` 기간을 등록한다. 자동 동기화와 담당자 저장 시 즉시 반영을 모두 보류한다. 예:

```sql
INSERT INTO sys_scheduler_business_hold (
    business_code, hold_start_at, hold_end_at, reason, reg_user
) VALUES (
    'HRM_ASSIGNMENT',
    '2026-10-09 09:00:00+09',
    '2026-10-09 18:00:00+09',
    '당일 대량 발령 등록 및 검증',
    '담당자계정'
);
```

### 실행 확인

`sys_scheduler_history`에서 작업 코드, 실행 계기, 시작·완료 시각, 처리 건수와 성공·실패·생략 사유를 확인한다. 실행 이력 테이블에는 인사 개인정보를 복제하지 않는다. 관리 화면과 로그인 후 사번 전환은 후속 기능이다.
